found bugs:

Bug 1 - [DONE] On a longer run i noticed the job itself got stuck at 50% along with the hashrate. the number of passwords tried
  Root cause: agent progress feed was purely event-driven off hashcat's --status-json stdout. If hashcat hung
  (driver stall / slow kernel) without exiting, hashcat_wrapper._stream_output looped on the readline timeout
  forever, yielding no events, so job_runner sent no progress and pct/hashrate/keys_tried stayed frozen. No
  watchdog, no timeout. Also: the branch's new stall-detection was defeated by the periodic hardware heartbeat
  refreshing progress_updated_at off a stale hashrate.
  Fix: (1) server only refreshes progress_updated_at on heartbeats carrying real progress_pct, not the hardware
  heartbeat's stale hashrate (agent_api.py). (2) agent stall watchdog in hashcat_wrapper: a tight silence limit
  (stall_timeout_seconds=120) AFTER the first status line, and a separate generous warmup limit
  (warmup_timeout_seconds=1800) BEFORE it so big jobs building the dict cache / autotuning are not killed at
  startup; on trip it kills hashcat and fails the job with a diagnostic message. Both knobs in config.toml.

Bug 2 - [DONE] "Recent Jobs" table on the dashboard renders timestamps with a 3h offset — they show UTC instead of the user's local time (user is in UTC+3 / EEST).
  Fix (server-side, dashboard-configurable): added server.display_timezone (IANA) to config, editable from the
  Settings page (new "Display Timezone" card + POST /settings/timezone, persisted to config.toml like the other
  settings). New Jinja filter `localdt` converts stored naive-UTC datetimes to that zone before formatting; all
  12 strftime sites across 9 templates now use it (datetime/date/time/datetime-sec tokens, with each site's
  original fallback preserved). Added tzdata to server requirements for cross-platform zone data; filter and
  config validator both degrade to UTC if the zone db is absent so startup never crashes. No DB migration.
  Note: all viewers (including kiosk) share this one configured zone — a per-viewer/browser TZ was not requested.

Bug 3 - [DONE] accounts cracked (while job running) shows 0, whereas the moment i cancelled the job, it showed me actual results.
  Root cause: cracked results are written to the DB only in submit_job_result, which runs at job END (complete or
  cancel — on cancel the agent still parses hashcat's outfile and submits, which is why cancelling "revealed" the
  count). During the run no Hash row is marked, so both job.cracked_count AND the batch rollup query
  (counts Hash.plaintext IS NOT NULL) read 0, and the dashboard's live tile reads exactly those. The agent parsed
  hashcat's recovered_hashes every status line but never transmitted it.
  Fix (Approach A — live count, no DB writes mid-run): agent now sends `recovered` in the live progress payload
  (job_runner); the WS progress handler caches it in ws_manager (new recovered cache, cleared at completion);
  dashboard_live surfaces it — per-job cracked_count = max(db, live recovered), and batch_cracked = db rollup +
  sum(live recovered of running siblings), capped at batch total. Authoritative deduplicated count still settles
  at job end via submit_result. Note: for batches the mid-run number is an approximation (possible transient
  overcount across siblings sharing a hash set); it reconciles exactly on completion.

Likely root cause: server stores datetimes as naive UTC (`datetime.utcnow()` everywhere) and Jinja renders them with `strftime` and no timezone conversion. First-seen offender is server/anvil_server/templates/dashboard/index.html:647 — `job.created_at.strftime('%Y-%m-%d %H:%M')` — but every `.strftime` across templates is probably affected (job detail pages, agent activity, audit log, etc.).

Two viable approaches when we tackle this:
 1. Client-side conversion (preferred): emit ISO-8601 with `Z` suffix inside `<time datetime="…Z">` tags, format with `Intl.DateTimeFormat` in JS so each viewer sees their own browser timezone. Kiosk mode would need a configured display TZ to avoid relying on the kiosk machine's clock setting.
 2. Server-side conversion: add a configurable TZ to settings.toml, convert UTC → site-local before strftime in a Jinja filter (e.g. `{{ job.created_at | localtime }}`). Simpler to implement, but everyone sees the same TZ regardless of browser locale.

Pre-work before either fix: audit whether model columns store naive vs. aware datetimes — if naive, decide whether to migrate to `DateTime(timezone=True)` or treat all naive values as UTC by convention.
